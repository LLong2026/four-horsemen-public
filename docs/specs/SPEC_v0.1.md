# MINTBOX-1 — a deterministic testnet box that moves a document claim

Working name. Research artifact, not a product. Private until the owner says otherwise.

Draft 2026-11-11. Status: design only. No chain activity has occurred under this spec.

---

## 1. The one sentence

**MINTBOX-1 issues one non-fungible claim per document, moves that claim only when both
parties sign, and proves after the fact that the claim existed, that the document it points to
is unchanged, and that every movement was the one recorded.**

If a feature cannot be traced to that sentence, it does not go in the box.

## 2. Non-goals, stated so they are never implied

- It is not a currency, not a payment rail, and not redeemable for anything.
- It does not store document bytes. It stores a commitment and a reference.
- It does not create, transfer, or perfect title to real property.
- It does not prove a document is true or that the parties agreed to it.
- It is not a notarization, a qualified timestamp, or legal advice.
- It does not issue on mainnet. Not with a flag, not with a config, not once "for a demo".

## 3. Roles, so the liability lands on the right party

| Party | Does | Wears |
|---|---|---|
| SQUIRL OS | builds and licenses the box | software liability, not securities |
| The buyer | runs the box, becomes issuer | the wrapper: terms, restrictions, disclosure, vertical rules |
| The box | executes signed transitions deterministically | nothing; it has no discretion |

The research artifact proves the mechanics. The buyer's legal review supplies the wrapper. Nothing in
this repository is an offering, and no token produced by it is offered for sale.

## 4. Box definition: one process, no discretion

ONE box. ONE box does not mean one server; it means one behaviour.

**Inside the box, there is no language model.** No agent, no planner, no summarizer, no
fallback to an LLM anywhere in a state transition. Model output may write prose into a report,
never into the ledger.

**Five verbs and no others:**

```
genesis   create the claim for a document digest
issue     make the claim holdable by a named holder
offer     propose a move, with an expiry
accept    the counterparty's signed consent, which completes the move
revoke    the issuer's clawback, which must be recorded, never silent
```

Everything else is a read. A `read` cannot change state, and a `read` may not be counted as an
event.

**One box, one file, one lock.** The box refuses to run twice: a lock file carrying the head
hash. Two boxes writing one ledger is a fault, not a scale-out.

## 5. The determinism contract

This is the part a fintech buyer actually pays for, so it is specified rather than assumed.

1. **Canonical bytes.** Every structure is serialized with JCS (RFC 8785): sorted keys, no
   floats, UTF-8, no whitespace variance. The digest is over those bytes only.
2. **No ambient inputs.** The clock, hostname, locale, random source, environment, and file
   mtimes are never read inside a transition. Time is an explicit field in the instruction. A
   transition that needs randomness carries it in the instruction, generated by the caller.
3. **Integer-only quantities.** No floats anywhere in the ledger. Amounts are strings of
   integers with an explicit scale.
4. **Signed instructions.** Every transition carries an Ed25519 or ML-DSA-87 signature over the
   canonical instruction. Unsigned means refused, with a stated reason.
5. **State is a fold.** `state = reduce(transitions, genesis_state)`. Any process that runs the
   same transitions from the same genesis reaches the same state.
6. **Rejection is deterministic too.** An invalid instruction produces the same refusal code and
   the same reason string every time. "It failed" is not a proof; `MINT-E-014 duplicate_issue`
   is.
7. **Head hash.** The ledger is hash-chained: `h_n = SHA-256(h_{n-1} || canonical(event_n))`.
   The head hash is published on every receipt, so a receipt pins the exact state it was issued
   under.
8. **Replay is a test, not a wish.** A fresh checkout replays the committed transition log and
   must reproduce the head hash byte for byte. Replay divergence is a critical finding, and it
   fails the build.

## 6. Testnet only, by absence rather than by flag

A flag can be flipped by a config edit, an environment variable, or a careless deploy. The
research build therefore does not contain the mainnet path at all.

- The network identifier appears in every artifact, in the clear: `network: testnet`.
- The code has no mainnet passphrase, no mainnet RPC endpoint, no mainnet horizon URL, and no
  mainnet chain id. Absence, not a boolean.
- Keys are generated inside a per-network namespace and are never reused across networks.
- The receipt refuses to render if the network field is missing or if it disagrees with the
  ledger's genesis record.
- A mainnet build, when a buyer wants one, is a separate build with separate keys and separate
  genesis. It is not this build with a switch.

## 7. The token model

**One document, one claim, amount 1.** The claim is non-fungible in meaning even where the
transport is a fungible asset, so the binding lives in the registry and is enforced on transfer.

Transport choice: a single issued asset on the testnet rail, with the 32-byte record digest in
the transfer memo. Rationale: one asset per record would need a trustline per record (0.5 XLM
each on Stellar) and would make every record a new asset class, which is both expensive and
legally noisy. One asset plus memo plus a registry is cheaper and keeps the binding explicit.

The honest cost of that choice: the transport units are fungible among themselves, so the box
must refuse a transfer whose memo does not match the registry's binding for that unit. That
check is the gate, and it is tested by trying to bypass it.

## 8. Why Stellar first

Stellar gives three things the design needs natively, and it is the cheapest rail that does:

- `AUTH_REQUIRED` plus `AUTH_REVOCABLE` plus clawback: the issuer controls who may hold, and can
  retract a fraudulent transfer at the ledger level rather than in a contract.
- **Claimable balances** are a two-sided acceptance primitive. The offer creates a balance with a
  named claimant and a time predicate; the move is not complete until the claimant claims it. The
  acceptance loop is the protocol's, not our code's.
- 32-byte `MEMO_HASH` carries the digest inside the movement itself.

Stated costs, because "free" is not a word this box uses:

| Item | Stellar testnet | Stellar mainnet equivalent |
|---|---|---|
| base fee per operation | 0.00001 XLM | 0.00001 XLM |
| account minimum | free from the faucet | 1 XLM (0.5 base + 0.5 per entry) |
| trustline | free from the faucet | +0.5 XLM each |
| each pending offer (claimable balance) | free from the faucet | +0.5 XLM held |

XRP Ledger is the second rail in a later milestone, for a buyer who wants two independent
witnesses: issuer `RequireAuth` on trust lines, 32-byte memo in hex, 10 drops burned per
transaction, 1 XRP base reserve plus 0.2 per object. Bitcoin is never a movement rail; it is the
free time layer (OpenTimestamps) that dates the receipt.

## 9. The event log and the receipt

Every transition appends one event:

```json
{
  "seq": 41,
  "verb": "accept",
  "network": "testnet",
  "record_id": "doc/digest/<sha256 of the document>",
  "holder_from": "did:key:z6Mk...",
  "holder_to": "did:key:z6Mk...",
  "rail": "stellar-testnet",
  "txid": "...",
  "memo_sha256": "<same 32 bytes, hex>",
  "offer_id": "ofr_...",
  "prev_hash": "...",
  "this_hash": "..."
}
```

The receipt is a rendering of the head hash plus the claim, and it carries the sentences a
reader needs: what is claimed, what is not claimed, which network, which digest, which
signatures, and which document reference a holder can go look at.

## 10. The auditor, and proving it can fail

The auditor is a second implementation, not a mode of the first. It re-derives state from the
event log and compares against the box's own head hash. It must be shown able to fail before it
is believed, by injecting each of these and confirming a refusal:

1. a second `issue` for an already issued record
2. an `accept` with no matching `offer`
3. an `accept` signed by the wrong party
4. an offer accepted after its expiry predicate
5. a memo that disagrees with the registry binding
6. a clawback with no recorded reason
7. an event with a broken `prev_hash`
8. a replayed event with a `seq` already present

A clean run and a failed run are both receipts. Only the pair demonstrates anything.

## 11. The milestone ladder

Each milestone ships with its acceptance test and its failure test, in that order.

| # | Milestone | Acceptance | Must also fail on |
|---|---|---|---|
| M0 | this spec, the repo, the claim sentence | owner reads it and agrees or corrects | n/a |
| M1 | deterministic core offline: genesis, issue, offer, accept, revoke, event log, replay | replay reproduces the head hash on a fresh directory | a clock read anywhere in a transition; a second `issue`; a broken `prev_hash` |
| M2 | Stellar testnet transport behind the core: faucet keys, issuer flags, trustline, claimable balance, memo hash | one document issued, one move offered and accepted, txids resolve on a testnet explorer with `network: testnet` | a transfer to an unauthorized trustline; an accept after expiry; a memo mismatch |
| M3 | receipts and the viewer: PDF/HTML receipt with head hash and attestation box, plus a read-only window | a stranger can check the receipt without the box | a receipt that renders with a missing or wrong network label |
| M4 | second witness: OpenTimestamps the receipt digest (free), optionally XRP testnet memo | receipt shows a Bitcoin block height and the XRP txid | a testnet txid presented as a mainnet anchor |
| M5 | auditor independence and fault injection: all eight injected faults caught | clean run and injected run both receipted | the auditor being the same code as the writer |

## 12. What a buyer must supply before any flip

Their own issuer keys in their own custody, a legal entity, terms that state what the claim does
and does not confer, a written answer from their attorney on two questions (is this offering an
investment contract, is this transfer money transmission or a document of title), and a mainnet
build with a separate genesis. None of that is this repository's to provide.

## 13. Repo discipline

Private by default. No operator personal data, no customer names, no keys, no wallet balances.
The export hygiene scan runs before any push. Every artifact carries `network: testnet` or says
`offline` explicitly.
